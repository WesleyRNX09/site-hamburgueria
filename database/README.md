# Banco de dados

Esta pasta é a fonte versionada da estrutura PostgreSQL, hospedada no
Supabase. O roteiro operacional completo está em
[`../docs/INSTALACAO.md`](../docs/INSTALACAO.md); a arquitetura de
personalização por estabelecimento (campos configuráveis, fallbacks, uploads e
como adicionar um novo campo) está em
[`../docs/PERSONALIZACAO.md`](../docs/PERSONALIZACAO.md).

| Caminho | Papel |
| --- | --- |
| `CRIAR_db.sql` | instalação nova e vazia: estrutura final + dados mínimos |
| `migrations/` | alterações incrementais depois da instalação (`npm run db:migrate`) |
| `mysql-legado/` | esquema, migrations e scripts da época do MySQL/MariaDB — só histórico, não roda no PostgreSQL |

## Fundação multiempresa

`estabelecimentos` é a entidade global que guarda nome, slug, domínio
personalizado, estado operacional, plano e situação da assinatura. `slug` é
obrigatório e único; o domínio personalizado também é único quando informado e
deve ser gravado como `NULL` quando não existir.

`configuracoes_estabelecimento` mantém uma configuração individual por
estabelecimento: URLs de logo/banner, paleta, fonte, contatos, endereço,
horários, opções de atendimento e pagamento e textos operacionais. Imagens
ficam fora do banco; somente URLs e caminhos são armazenados.

`schema_migrations`, `metadados`, `superadministradores`, `sessoes_superadmin`
e `auditoria_superadmin` são globais; a própria tabela `estabelecimentos` é o
registro global dos tenants. As demais tabelas de negócio têm
`id_estabelecimento`, inclusive itens e sessões, para permitir filtros simples
e auditoria sem depender só de relacionamentos indiretos. A tabela
`configuracoes` é mantida como compatibilidade temporária;
`configuracoes_estabelecimento` é o modelo definitivo.

O backend resolve o estabelecimento somente pelo `Host`: subdomínio do domínio
principal, domínio personalizado ou slug de desenvolvimento em localhost. O ID
do estabelecimento enviado pelo cliente não é usado.

## Convenções do esquema

- Chaves geradas: `BIGINT GENERATED BY DEFAULT AS IDENTITY`. A lista de tabelas
  com id gerado fica também em `COLUNAS_IDENTIDADE`
  (`server/db/postgres.js`), que devolve o `insertId`; o teste de segurança
  compara as duas.
- Horários: `TIMESTAMPTZ`. O pool fixa a sessão em UTC.
- Flags: `SMALLINT` 0/1, o mesmo valor que o backend lê e grava.
- Valores em centavos: `BIGINT` com `CHECK (coluna >= 0)`.
- Unicidade de usuário, e-mail e nomes do catálogo ignora maiúsculas
  (`CREATE UNIQUE INDEX ... (id_estabelecimento, LOWER(nome))`).
- `atualizado_em` é mantido pelo gatilho `definir_atualizado_em()`.
- **RLS ligado em toda tabela, sem políticas.** O Supabase publica o schema
  `public` pela API REST com a chave `anon`, que é pública; sem RLS, qualquer
  pessoa leria os dados de todas as lojas. O backend conecta como dono das
  tabelas e não é afetado. Toda tabela nova precisa de
  `ALTER TABLE <tabela> ENABLE ROW LEVEL SECURITY;` — o teste de segurança
  cobra isso no `CRIAR_db.sql` e em cada migration.

## Instalação nova no Supabase

1. Crie o projeto no Supabase.
2. Abra **SQL Editor**, cole o conteúdo inteiro de `CRIAR_db.sql` e execute.
   Tudo roda numa transação: se algo falhar, nada fica pela metade.
3. Configure `DATABASE_URL` (Session pooler), `DB_SSL=true` e `DB_SSL_CA` no
   `.env` (ver [`../env.example`](../env.example)).
4. Defina senhas fortes para o administrador do estabelecimento inicial e para
   o superadministrador global. Execute `npm run criar-admin-inicial` e
   `npm run criar-superadmin`.
5. Valide com `npm run db:check`. No SQL Editor, esta consulta não pode
   devolver linha nenhuma (toda tabela com RLS):
   `SELECT tablename FROM pg_tables WHERE schemaname = 'public' AND NOT rowsecurity;`

`CRIAR_db.sql` contém tabelas, índices, relacionamentos, gatilhos, RLS, o
estabelecimento inicial de compatibilidade e apenas dados iniciais não
sensíveis. Ele não contém conta administrativa nem dados demonstrativos, e não
executa `CREATE DATABASE`.

## Preparação explícita

`npm run db:prepare` é uma conveniência para um schema novo e vazio: aplica a
estrutura (o trecho entre `-- @@ESTRUTURA_INICIO@@` e `-- @@ESTRUTURA_FIM@@`
do próprio `CRIAR_db.sql`, então não existe segunda cópia do esquema) e cria o
primeiro administrador a partir do `.env`. O comando recusa qualquer schema que
já contenha tabelas, evitando que uma reinstalação altere dados existentes.

Dados fictícios são opt-in: somente `SEED_DEMO_DATA=1` faz o preparo inserir o
catálogo e a operação de demonstração. Use essa opção apenas em ambiente
descartável; ela deve permanecer desativada em produção.

O servidor (`npm run dev`, `npm start`) apenas abre e valida a conexão. Ele não
cria banco, tabelas, índices, relacionamentos, usuários ou seeds no startup.

## Banco existente e migrations

Nunca execute `CRIAR_db.sql` em um banco persistente. Antes de alterar um banco
existente:

1. crie um backup e teste a restauração em ambiente isolado;
2. valide as variáveis com `npm run db:check`;
3. revise as migrations pendentes em `migrations/`;
4. execute `npm run db:migrate` em uma janela controlada;
5. rode os testes da aplicação.

Detalhes do formato em [`migrations/README.md`](migrations/README.md).

## TLS e segredos

- Nunca versione `.env`, senha, token, chave privada, certificado ou backup real.
- Use um `JWT_SECRET` aleatório com pelo menos 32 bytes e compartilhe o mesmo
  valor entre todas as instâncias do mesmo ambiente.
- A senha do banco fica só no backend (`DATABASE_URL`/`DB_PASSWORD`); nunca no
  frontend.
- Habilite `DB_SSL=true` e informe em `DB_SSL_CA` o caminho do certificado do
  Supabase ou o conteúdo PEM (quebras como `\n`). A validação do certificado
  não é desativada.
- `SYNC_ADMIN_CREDENTIALS=1` pode atualizar a primeira conta administrativa;
  use-o apenas de forma pontual e volte a `0` após a recuperação controlada.
- `SYNC_SUPERADMIN_CREDENTIALS=1` faz o mesmo para a conta global e revoga suas
  sessões existentes; volte a `0` imediatamente depois do uso.

## Painel global e novos estabelecimentos

Defina `SUPERADMIN_USER`, `SUPERADMIN_EMAIL`, `SUPERADMIN_NAME` e uma
`SUPERADMIN_PASSWORD` com pelo menos 12 caracteres. Execute
`npm run criar-superadmin` uma única vez e acesse `/superadmin/login`. A senha
é transformada em hash antes de ser gravada e não é criada no startup da
aplicação.

O cadastro de um estabelecimento pelo painel cria, na mesma transação, o
tenant, sua configuração visual e o primeiro administrador. Não execute
`CRIAR_db.sql` novamente para cada cliente. Plano, situação e vencimento da
assinatura são controles manuais; não há gateway de cobrança.

Para publicar um novo slug como subdomínio, configure um registro DNS curinga
para `*.seu-dominio` apontando para a mesma implantação e preencha
`DOMINIO_PRINCIPAL`. Um domínio personalizado também precisa ser apontado no
DNS para essa implantação antes de ser informado no painel. DNS, certificado
TLS e configuração do proxy/hospedagem não podem ser realizados pela aplicação.
